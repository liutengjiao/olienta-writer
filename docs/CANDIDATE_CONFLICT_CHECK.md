# 候选稿冲突检查

Olienta 的候选稿冲突检查不替作者做决定，只把风险提前说清楚。最终采用权永远在作者手里。

## 触发时机

生成候选稿，或保存手动修改后的候选稿时，系统会立即审查，并写入：

```text
manuscript/candidates/reviews/{章节号}.md
```

候选稿本身仍然保存在：

```text
manuscript/candidates/{章节号}.md
```

## 当前检查范围

- 基础文本检查：AI 味、完整性、章节钩子。
- 蓝图检查：本章必须发生、禁止提前发生。
- 事实检查：已确认事实、禁止违背规则。
- 伏笔检查：未闭合伏笔是否被提前回收。
- 角色检查：角色卡、关系图谱、成长线。
- 时间轴检查：Timeline Pro 开启后，检查未来里程碑是否被提前触发。

## 角色卡检查

角色检查读取：

```text
characters/cards/*.md
characters/relations.md
characters/growth.md
```

如果候选稿提到某个角色，却没有承接角色卡中的定位、欲望、恐惧、关系或不可误写边界，会出现“角色提醒”。

如果候选稿包含否定表达并触碰角色卡边界，会出现“角色风险”。

## 时间轴检查

时间轴检查只在以下条件同时满足时启用：

```text
.olienta/timeline-settings.json
enabled = true
conflictCheck = true
```

启用后读取：

```text
timeline/events.md
timeline/milestones.md
```

检查重点：

- 当前章节是否提前触发未来章节里程碑。
- 是否提前揭开真相、高潮、终局、伏笔回收。
- 是否出现“真相大白”“水落石出”“最终答案”等解决式表达。

风险会以“时间轴高危”写入审查报告。

## 界面分组

正文草稿里的“审查清单”会按来源分组显示：

- 时间轴及里程碑。
- 章节蓝图。
- 事实库与禁止规则。
- 角色边界。
- 伏笔与回收。
- 文本质量。
- 生成与任务书。

分组只是为了让作者更快判断风险来源，不改变采用权限。作者仍然可以修改任意文字，也可以带着风险采用候选稿。

同样的分组也会写入本地审查报告：

```text
manuscript/candidates/reviews/{章节号}.md
```

因此作者即使不在软件界面里，也可以直接打开 Markdown 报告查看风险来源。

## 设计原则

- 检查结果是提醒，不是拦截。
- 作者可以带着风险采用候选稿。
- 一旦采用并保存正文，正文进入作者确认链，后续 AI 必须尊重。
- 所有检查依据都来自本地可读文件，不依赖隐藏数据库。
